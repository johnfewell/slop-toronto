# Toronto Islands cottage footprint audit (st-sb3r.30)

Read-only audit of the accepted island cottage rows: the real OpenStreetMap building polygon versus the rendered
geodata row's part rectangles, measured in the renderer's own frame. It tests the hypothesis ("the rows are wrong
because several mapped cottages were merged into one native footprint") rather than assuming it, and reports what is
actually off. No runtime file, `data/toronto-geodata.bin`, generated profile, collider or camera is changed.

Reproduce (all local, no network at run time):

```sh
node tools/audit-island-cottage-footprints.mjs          # human summary
node tools/audit-island-cottage-footprints.mjs --json   # machine report
```

Exit `0` = every accepted record bound to a committed row + cached source way and every metric self-check passed. Exit
`1` = a required input is missing/malformed, a record failed to bind, or a metric self-check failed (it fails loudly
rather than reporting on a partial or invalid set).

## What it measures (per record, in the row's own frame)

Every accepted record names its OSM way and a footprint signature (`fp` = yaw + part rectangles). The tool binds a
record only when (a) a committed row has its rounded world centre, (b) that row's yaw + parts reproduce `fp` exactly
(the runtime's `footprintMatches` guard), and (c) the way id is in the cached source. All 331 bind.

- **Source polygon** projected with the generator's exact `toWorld` and rotated into the row frame
  (`worldx = cx + u·cos + v·sin`, `z = cz − u·sin + v·cos`); the inverse is the rotation the tool applies.
- **Rendered union**: the union of the row's drawn part rectangles (only parts ≥ 1 m, i.e. the ones `buildings.js`
  renders), sampled on a 0.1 m grid — never a sum of overlapping rectangles.
- `areaRatio` = rendered union / source polygon; `iou`, `covSrc` (fraction of mapped footprint covered), `covRen`
  (fraction of drawn inside mapped).
- `rectangularity` = source polygon area / its minimum-area bounding rectangle: 1 = the mapped outline is a rectangle,
  lower = real notches/offsets/attached mass that an axis-aligned rectangle cannot hold.
- `srcLongAxisDeg` = error between the mapped rectangle's long side and the row's own axes, folded **modulo 90**. A
  rectangle has a two-fold axis class, so 0/90/180/−90° are the same alignment (0° error) and the value is always in
  `[0, 45]`. This is measured in the local frame against the row axes, not against the global row angle (that would be
  circular).
- **Merged-frontage test**: another island building way whose vertex-mean point lands strictly inside this row's rendered union
  This is a screening heuristic, not a proof that distinct buildings were merged; concave geometry and overlapping source ways require individual review.

### Metric self-checks (the audit cannot silently pass an invalid statistic)

- Axis-error self-check on known angles *before* the record loop: `0/90/180/−90 → 0`, `44 → 44`, `46 → 44`, `135 → 45`,
  `−45 → 45`. A wrong fold fails the run (verified: forcing `angDiff90` to a plain difference makes it stop with
  `axis-error self-check: 90 deg -> 90.000000, expected 0`).
- After aggregation every `rotationErrDeg` value is asserted in `[0, 45]` for both the full set and the cottages. A
  negative mean is exactly the invalid statistic an earlier revision produced; it now fails rather than reports.

## Findings (2026-11-10 run, 331 bound, 265 cottages)

**1. Merged frontage is not the dominant error — the premise is mostly false.** Only **2 / 331** rows hold more than one
source centroid, and both are named pavilion/washroom clusters at Hanlan's Point and Blockhouse Bay, not cottages:

| Row (OSM way) | parts | src ways inside | areaRatio | IoU | category |
| --- | --- | --- | --- | --- | --- |
| 1375105739 (Blockhouse Bay) | 4 | 1375105737/738/740 | 1.90 | 0.28 | service |
| 711107323 (Hanlan's Pavilion) | 4 | 638632056/711107322/1375105746 | 1.49 | 0.37 | service |

Of the remaining rows, **327** contain one source vertex-mean point and **2** contain none; native part rectangles are essentially 1:1 with the mapped way. So
"several cottages merged into one row" is not the mechanism behind the repeated low-cottage look.

**2. The real footprint error is outline/notch loss, and it is moderate.** Cottages: mean IoU **0.722**, median 0.737,
p10 0.63; area ratio mean **0.993** (p10 0.79, p90 1.13 — no systematic over- or under-size); renderer covers 0.835 of
mapped, 0.846 of drawn is inside mapped. **158 / 265** cottages map a non-rectangular outline (rectangularity < 0.95);
mean rectangularity 0.914 (p10 0.80). Both position/size offsets and lost re-entrant outlines contribute. The renderer draws every retained rectangular part; the largest part is used for cottage eave sizing and trim. OSM footprint shape alone does not identify a notch as a porch. Worst under-cover (renderer drops
real mapped mass), cottages only:

| OSM way | street | areaRatio | IoU | rectangularity |
| --- | --- | --- | --- | --- |
| 487167567 | Nottawa Ave | 0.545 | 0.47 | 0.999 |
| 795796148 | Ojibway Ave | 0.620 | 0.59 | 0.792 |
| 795795980 | Willow Ave | 0.631 | 0.51 | 0.719 |
| 795795971 | Second St | 0.642 | 0.49 | 0.681 |
| 795796171 | Ojibway Ave | 0.651 | 0.56 | 0.770 |
| 795796037 | Dacotah Ave | 0.653 | 0.59 | 0.794 |

Worst overall IoU among cottages is achieved on square-ish outlines that the rectangle holds poorly against a diagonal
aspect (e.g. 334683126 Bayview, 487167568 Nottawa: IoU ≈ 0.39–0.42, IoU limit from the shape, not mass loss).

**3. Rotation is faithful — not the error.** Mod-90 axis error against the row axes: mean **0.1°**, p90 0.3°; all 265
cottages within 10°. The generator already aligned each row's yaw to the mapped long side; there is no orientation
deficit to fix and no basis to invent one.

**4. The visible repetition is style, and the source cannot currently correct it.** Every one of the 265 cottage
records has `roofSource` / `sidingSource` = `island cottage typology approximation` and `heightSource` =
`conservative island estimate` (263; 2 use OSM levels). Roofs are an id-keyed 186 gable / 79 hip split; 264 of 265
heights are the single 6.5 m estimate. The cached source has **0** residential `roof:shape`, **0** `roof:orientation`,
**0** `height`, **0** `building:material` (1 `building:colour`) tags. So the elevation/roof sameness is an approximation
we cannot ground per house from this snapshot — it is not a footprint defect.

### Scope, stated precisely

- Not merged frontage (2/331, both service pavilions).
- Moderate notch/outline loss on non-rectangular cottages (IoU ~0.72), with mean axis error 0.1° (p90 0.3°).
- Repetition is un-sourced style, with no OSM tag support in this snapshot to differentiate it.

## Bounded next correction

The street-view repetition is primarily the shared facade/height/roof approximation. **st-sb3r.31** addresses the observed dense window rhythm and door/shader alignment; it remains explicitly generic cottage typology rather than an exact per-house elevation.

For a subsequent geometric pass, start with **one demonstrably rectangular source footprint**, OSM **487167567** on Nottawa Avenue: rectangularity 0.999, rendered/source area ratio 0.545. Verify its current OSM geometry and identity before changing it. Its major size mismatch is a clearer first target than replacing all 158 non-rectangular outlines.

A possible bounded producer is a source-matched profile override for that row's effective local rectangle, guarded by the existing original footprint signature. In `js/buildings.js`, the same effective parts must drive walls, roof, trim and the generated OBB colliders. `main.js` passes these colliders to the controller and camera collision system. Retaining an old smaller collider while expanding a visual wall is **not acceptable**. Also check source canopy trunk exclusions, yard classification and any native-GEO spatial consumers against the effective footprint.

Do not simply activate the existing `?massing=1` path: `buildings.js` gates the cottage extension with `!foot`, so that would disable accepted cottage siding/roofs. A non-rectangular polygon pass needs a profile-aware renderer and matching movement/camera obstacles. It is not implemented by this audit.

The cached source supplies no residential roof-orientation tags. Footprint-axis alignment does not establish a roof ridge direction, and per-house roof or colour changes need additional evidence.

## Limits

- Footprint and IoU figures are polygon geometry comparisons of the committed OSM snapshot (ODbL), not a survey or a
  ground measurement; OSM outlines can lag or simplify a building.
- The style finding is about the accepted *approximations*, not a claim that any specific house has a specific roof.
- Roof-orientation exactness cannot be audited from this snapshot because OSM carries no `roof:orientation`; that is a
  data gap, not an error in the current approximation.
- Read-only: no resident/private information is used or exposed.
