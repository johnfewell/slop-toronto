# Durable geodata and transit identities (MD)

Status: implemented for `st-wt0.7`, the MD prerequisite of AR-9 in
the adoption spec (internal, not published here). It gives later manifests
(storefronts, facades, passage/quay, the operator pilot) something durable to key on. It does not add any of
those features, and nothing new is loaded at startup.

## What is emitted

`js/toronto-geodata.js` keeps its format and its bytes: rebuilding it after this change gives an identical file.
Its rows stay positional. **Positions are for in-session use only and are never persisted.**

`js/toronto-geodata-ids.js` (`window.CITY.GEO_IDS`, generated by `tools/build-geodata.mjs` in the same run) is the
sidecar for those rows. The build writes it beside its `--out` script (`out-ids.js`) unless `--ids <file>` names it; the
packed `data/toronto-geodata.bin` it also writes is the same `GEO`, so the hash below holds for both.

| Field | Meaning |
|---|---|
| `schema` | `1` |
| `geodata` | first 16 hex digits of the SHA-256 of the exact `js/toronto-geodata.js` it describes. A consumer must check this before trusting the row alignment. |
| `pois[i]` | the OSM element of `GEO.pois[i]`: `osm:node/…`, `osm:way/…` or `osm:relation/…` |
| `poiAliases` | an element left out as a duplicate (same name within 60 m) → the place ID that was kept |
| `buildings[i]` | the City of Toronto 3D Massing record of `GEO.buildings[i]`: `to-3dmassing-2025:<record>` (`.<polygon>` for the 80 multi-polygon records) |
| `buildingOsm[i]` | the OSM footprint that gives the building its type/name, or `''`. Not unique: a tower and its podium share one footprint. Use it to match a POI to its building, not as a building ID. |
| `landmarks` | `CITY_LANDMARKS`/`GEO.landmarks` id → the OSM element its outline came from |
| `aliases` | authored aliases from `tools/data/geo-id-aliases.json` |

The sidecar is about 1.9 MB. Pages don't reference it, so `tools/build-site.mjs` doesn't ship it until a feature
loads it (lazily, within the startup payload gate).

`js/toronto-transit.js` patterns each gain an `id`. `patternAliases` carries authored pattern aliases. All other
fields are unchanged; in the 2026-09-30 feed they are byte-identical to before.

## ID forms

- **OSM:** `osm:<type>/<id>`. `<type>` is the true OSM type. `tools/fetch-osm.mjs` reshapes a closed way that the
  city box cuts into pieces as a relation, and records its type as `osmType: 'way'`. Six footprints and one POI in
  the current extract are such ways; before this change they were indistinguishable from relations.
- **3D Massing:** the 2025 shapefile has no feature-ID column. The source ID is the record number (shapefile FID,
  from 0) within the named edition (`tools/fetch-massing.mjs` writes `fid`, `k` and `edition`). A record number
  means nothing in another edition, so a new edition is a new dataset prefix (`MASSING_EDITIONS` in
  `tools/geo-ids.mjs`). Records that matter are carried across with aliases; unmatched ones lose their records.
- **Face:** `<building ID>:n|e|s|w`. This is the side of the building's plan facing grid north (−z), east (+x),
  south (+z) or west (−x). `faceOf(row, side)` in `tools/geo-ids.mjs` gives the wall:
  - its ends `a` → `b`, left to right as seen from outside
  - its outward normal, width and height
  Wall-local extents in manifests are metres from `a`. The wall spans the plan's whole extent on that side; picking
  the part of a stepped plan is the manifest's job. A plan within 45° ± 5° of the grid has no reliable compass side,
  so `faceOf` returns `null`: such buildings can't take face records.
- **Transit pattern:** `ttc:<GTFS route_id>:<direction_id>:<runs as 0|1|3>:<stops hash>[:<variant>]`.
  - The stops hash is the first 10 hex digits of the SHA-256 of the ordered GTFS `stop_id`s the pattern calls at
    inside the detailed city.
  - "Runs as" is the existing replacement-bus rule.
  - First/last stops alone are not an identity. Raw route/stop indexes and GTFS `shape_id`s are not durable.

## Rules the build enforces

- Inputs are processed in source order before anything is chosen (`byOsmKey`, `byMassingRecord`):
  - OSM elements sort node < relation < way, then by id.
  - Massing parts sort by record, then polygon.
  This is the order the extracts already come in, so the output is unchanged, and the first-match choices no longer
  depend on file order. Those choices are the de-duplicated places, the footprint that names a building (ties broken
  by OSM key) and the landmark outline.
- Two rows with one ID fail the build. So does an alias that shadows a live ID or points at nothing.
- Transit patterns are grouped by their full identity **before** the TTC's per-time-band shapes are merged, so a
  branch with different intermediate stops keeps its own pattern. (The old key was positional route index,
  direction, first stop, last stop and type. In the current feed it happened not to merge any distinct stop
  sequences.)
- Shapes in one identity are compared between its first and last stop, both ways, sampled every 10 m. If they stray
  more than 20 m apart the build fails, until `tools/data/transit-variants.json` records one of:
  - a `variants` entry, which gives the shapes that pass `near` a point their own `key`
  - a `reviewed` decision `{ pattern, same: true, maxStray, note }`, saying they are one path within a bound

  One decision is recorded: route 94A westbound's two shapes differ only in the loop into Ossington Station (85 m,
  beside Bus Bay 4).
- `idResolver(GEO_IDS)` in `tools/geo-ids.mjs` is for manifest compilers. It resolves place, building and face IDs
  through `poiAliases` and `aliases`. Anything else is `null`, and that record is dropped, never re-attached to a
  nearby feature.

## Aliases and version changes

- Add `"<old ID>": "<live ID>"` to `tools/data/geo-id-aliases.json` (places/buildings), or to `aliases` in
  `tools/data/transit-variants.json` (patterns), when a source ID changes for the same real feature. Examples: a new
  massing edition, an OSM feature re-mapped, the city box or a stop list changing a stops hash.
- Aliases don't chain. A schema change bumps `schema`.

## Verification

- `node --test tests/geodata-ids.test.mjs` needs no raw data. It checks:
  - the committed sidecar's hash, counts, ID forms and uniqueness
  - the transit ID form and uniqueness
  - order independence of the sorts
  - face geometry, including the 45° refusal
  - resolver/alias failure cases
  - a synthetic GTFS feed showing that a same-endpoint branch stays distinct, a different-street shape needs a
    reviewed variant, a "same" decision is bounded, and pattern aliases are checked
- `GEO_DATA=~/.cache/slop-toronto/osm-ids node --max-old-space-size=12288 tools/check-geodata-ids.mjs` needs the
  raw downloads. It rebuilds from shuffled `osm_pois.json`, `osm_buildings.json` and `massing.json`, and from a
  shuffled GTFS `trips`/`stop_times`/`shapes`. 28 October 2026 result, seed 20261028:
  - the geodata is byte-identical to the committed file
  - 13,657/13,657 place IDs, 35,266/35,266 building IDs and their footprints resolve to the same rows
  - 141,064 face lookups resolve to the same walls
  - 96/96 pattern IDs resolve to the same route, path and stop IDs

## Raw-data cache

The ID build needs inputs regenerated by the updated fetch scripts. `~/.cache/slop-toronto/osm-ids` holds them:
- `fetch-osm.mjs` re-run on the same 23 October Ontario extract
- `fetch-massing.mjs` re-run on the same 2025 shapefile
- symlinks to the unchanged DEM and City roadway

They match the previous `~/.cache/slop-toronto/osm` files except for the added `osmType`/`fid`/`k`/`edition`
fields and the converter's synthetic node numbers. The older cache is left as it was. Building from it now stops with
a message to re-run `tools/fetch-massing.mjs`.
